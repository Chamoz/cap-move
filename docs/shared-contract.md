## 1. Data

- Source: CAP `cap_detection_handheld_val` (Visym Labs, CC BY 4.0, https://registry.opendata.aws/visym-cap/).
  Local copy: `data/cap_detection_handheld_val/` (47 videos, 47 vipy JSON annotations, 32 collectors).
- Ground truth: vipy JSON `activities` (label, startframe, endframe, actorid) and `tracks`
  (person boxes, keyframes, linear interpolation). `cap_detection_handheld_val_ref.csv` is NOT used:
  it differs from the JSON by ±1 frame on most rows and does not carry track or collector ids.
- Stage A uses only this file. Stage B rules are in §7.

## 2. Data rules (mandatory)

1. Never try to identify a person. No face recognition, no person re-identification across videos,
   no biometric embeddings stored or compared.
2. Subjects are referred to only by `collector_id` (UI may show the first 8 characters).
   The fields `subject_ids`, `ipAddress`, `device_identifier` must not be read into any artifact,
   log, UI, or output.
3. Frames, clips, thumbnails and derived pixels stay inside this environment: no upload to external
   APIs or hosted models, no git commit of media. Media folders (`data/`, `artifacts/`) are git-ignored.
4. Attribution "Consented Activities of People (CAP), Visym Labs, CC BY 4.0" is shown in the tool and README.

## 4. Segments and manifest

- One segment = one annotated activity instance whose label maps to a §3 class.
- `segment_id = "{video_id}__{activity_id}"` (activity id from the vipy JSON).
- Overlapping annotations (the same action annotated twice) are kept as separate segments.
- `manifests/val_segments.csv` is generated by `scripts/build_manifest.py` (deterministic).
  Frozen v0.1 content: 167 segments, 41 videos, 28 collectors,
  sha256 `66181cb255b14c8d3e0adcb188694f0bfb10461435975905f0a9c5e3bd74f321`.
- Columns: `segment_id, fold, class, confusable_pair, raw_label, video_id, video_path, collector_id,
  collection_name, track_id, start_frame, end_frame, fps, frame_width, frame_height, device_type`.

## 5. Evaluation protocol

- 5-fold cross-validation grouped by `collector_id`. Each collector is in exactly one fold. Folds are
  stratified by class with a seeded search (seed 20261003); the `fold` column in the manifest is authoritative.
- Out-of-fold: the prediction for a segment in fold k comes from a model whose trained or fitted parts
  (classifier head, calibration parameters, abstention threshold, any hyperparameter selection) used
  only segments from the other 4 folds. Nothing from fold k may be used to fit its own predictions.
- Pretrained weights may be used frozen or fine-tuned, provided they were not trained on CAP. Every
  weight file is listed in `predictions.json` → `run.weights` and in `docs/weights.md`.
- Temporal boundaries: `predictions.json` scores classification of the given ground-truth segments
  (oracle boundaries, the given `track_id` box). The review tool also runs open-world on uploaded video
  (detect → track → temporal segmentation). That path is demonstrated and spot-checked, but it is not
  part of the score.

## 6. Scoring rules

Computed by `scripts/score.py` over all manifest segments; a missing segment is a hard failure.

| metric | definition |
|---|---|
| Accuracy, Macro-F1 | argmax of `probs` over all segments (abstained ones included) |
| ECE | 10 equal-width bins on `confidence` = max(`probs`) |
| NLL, Brier | from `probs` against the true class |
| Coverage | fraction with `abstain = false` |
| Selective accuracy | accuracy on non-abstained segments |
| AURC | area under the risk–coverage curve, ranking segments by `confidence` |
| Confusable-pair error | per pair: share of that pair's segments predicted as their pair-partner class |

- Primary metrics: AURC (lower is better) and ECE (lower is better), reported with Macro-F1, and with
  coverage and selective accuracy at the run's operating threshold.
- Baselines reported alongside: uniform prior, and the uncalibrated model (temperature = 1).
- Breakdowns: per fold, per class, per confusable pair, per collector, and per viewpoint proxy
  (`device_type` family iOS/Android, resolution, fps bucket, and person-box scale small/medium/large
  from the GT track). The failure gallery draws on these same breakdowns.

## 7. Stage B (optional)

- Train on the 8 classes extracted from ONE trainval archive in `s3://consented-activities-of-people/train/`
  (`cap_classification_clip.tar.gz` 308.7 GB or `cap_classification_pad.tar.gz` 414.9 GB).
- Exclude every trainval clip whose `collector_id` appears in the val file (all 32 val collectors).
- The val manifest remains the only evaluation set; Stage B is reported as a separate run
  (`run.stage = "B"`) next to Stage A, with the same out-of-fold rule for anything fitted on val.
- Store data in a dedicated bucket or prefix, never in `cdk-hnb659fds-assets-*`.
- Cost and time estimate plus explicit user approval are required before the pass starts.

## 8. Deliverables

`predictions.json` (valid against `configs/predictions.schema.json`, every manifest `segment_id`
exactly once), `docs/weights.md`, `docs/effort-log.md`, and the review tool.
